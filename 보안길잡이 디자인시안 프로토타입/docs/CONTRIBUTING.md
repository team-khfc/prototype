# 보안길잡이 AI 팀 공통 개발 규칙

상태: 팀 검토용 초안 v0.1 · 작성일: 2026-11-05

이 문서는 사람과 AI가 함께 개발할 때의 협업 기준이다. Google 가이드는 코드 스타일의 참고 자료이며 아래 브랜치·리뷰·아키텍처·업무 정책은 보안길잡이 팀의 제안 규칙이다. 적용 여부는 팀 채택 PR에서 확정한다.

## 1. 문서별 책임

| 문서 | 담을 내용 | 변경 검토 책임 |
|---|---|---|
| README.md | 현재 구현 범위, 설치·실행, 주요 경로 | 변경 기능 담당자 |
| CONTRIBUTING.md | 협업 절차, API·데이터·검증 공통 원칙 | 팀장 + 영향받는 담당자 |
| CODING_STYLE.md | 언어별 작성 규칙, formatter/linter와 예외 | 프런트·백엔드 담당자 |
| AGENTS.md | AI가 따라야 할 짧고 실행 가능한 지침 | 개발 담당자 |
| backend/AGENTS.md (후속 작성) | 백엔드의 작업·검증 추가 지침 | 백엔드 담당자 |
| design.md | KRDS 토큰·UI·상호작용·접근성의 기준 | UI/UX 담당자 |
| specs/spring-v3-contract.md | v3 API 제안, 서버 책임; 이후 확정 계약으로 발전 | 프런트 + 백엔드 |
| docs/adr/ | 도구·구조·인증·저장소의 주요 결정과 이유 | 결정의 영향받는 담당자 |

동일 규칙을 여러 문서에 길게 복사하지 않는다. AGENTS.md는 핵심 제약과 원문 경로를 안내한다. 세부 규칙이 충돌하면 분야별 기준 문서와 채택된 ADR을 확인하고 모순을 수정한다.

## 2. 현재와 목표를 구분한다

현재 소스 확인 기준: commit `7c168bde1578ef483db1b49fd3fba367ec87bdb8`.

- 프런트엔드: 루트의 Next.js 16.3.4, React 19.2.6, TypeScript 5.9.3, npm lockfile.
- 백엔드: backend/의 Java 21, Spring Boot 3.5.16, Maven.
- v3 화면은 sessionStorage 기반이며, v1 인메모리 API는 별도의 예제다.
- 실제 인증·기관 권한·AI·Oracle DB 연동은 구현 예정이다. 검토 문서만 존재하는 기능을 완료로 표시하지 않는다.
- Node.js는 Dockerfile의 22 계열을 팀 기준으로 삼되 CI·로컬의 지원 패치 버전을 함께 고정한다. 최신 버전으로 자동 변경하지 않는다.
- 실행법과 Docker 한계는 기존 README.md·DOCKER.md를 따른다. 과거 테스트 기록은 현재 PR의 실행 결과와 구분한다.

## 3. 5인 팀의 책임 배치 예시

| 역할 | 주 책임 | 상호 검토 |
|---|---|---|
| 팀장 | 범위·우선순위·일정·통합·릴리스 판단 | 구조 변경·핵심 업무 규칙 |
| 기획·UI/UX | 사용자 흐름·문구·수용 기준·design.md | 화면·접근성·업무 의미 |
| 개발자 A | React·Next.js·공통 컴포넌트 | 프런트 변경·API 계약 |
| 개발자 B | Spring Boot·권한·업무 상태·DB | 백엔드 변경·API 계약 |
| 기획·개발 | 기관 질문·AI 흐름·통합 테스트·문서 | 시나리오·연계·회귀 확인 |

역할은 예시다. 이슈마다 구현 책임자 1명과 검토자 1명을 지정하고, 특정 사람만 수정 가능한 독점 영역은 만들지 않는다. 실제 Git 계정을 확정한 뒤 CODEOWNERS를 작성한다.

## 4. 이슈 → 브랜치 → PR → 병합

1. 이슈에 문제·사용자 역할·포함 범위·완료 조건·영향 화면/API를 쓴다.
2. `main`에서 짧은 작업 브랜치를 만든다. 초기 5인 팀은 상시 develop 브랜치 없이 시작한다.
3. `feat/123-review-request`, `fix/124-session-restore`, `docs/125-api-contract`처럼 목적과 이슈를 표현한다.
4. PR은 한 가지 변경 이유를 중심으로 구성한다. 의미 없는 줄 수 제한보다 리뷰 가능한 범위를 우선한다.
5. 커밋은 `feat(review): 담당자 보완 요청 추가`처럼 유형·영역·변화를 기록한다. 이 형식은 팀 규칙이다.
6. 작성자 이외 최소 1명이 검토하고 필수 CI가 통과하면 squash merge한다. 실제 branch protection 설정은 별도 적용한다.
7. 인증·기관 분리·제출·DB 파괴적 변경은 관련 담당자가 반드시 검토한다. 검토 인원 수만 늘려 책임을 흐리지 않는다.
8. main에 직접 push하거나 보호 규칙을 우회하지 않는다. 긴급 예외는 사유·추적 이슈·후속 검토를 남긴다.

기능 변경과 대량 포맷 변경은 별도 PR로 만든다. 파일 이동·이름 변경도 영향이 크면 분리한다. 리뷰 의견은 오류·규칙 위반·개선 제안을 구분하고 단순 취향으로 병합을 막지 않는다.

## 5. 코드와 아키텍처의 공통 경계

| 영역 | 책임 | 피할 일 |
|---|---|---|
| React | 표시, 입력 상태, 사용자 피드백 | UI 값으로 서버 권한 확정 |
| Next.js | 라우팅, 페이지 구성, 렌더링·서버 경계, 필요한 프록시 | Spring Boot와 별도의 업무 승인 로직 운영 |
| Spring Boot | 인증·기관 범위·업무 전이·저장·감사 | 브라우저의 role 값을 그대로 신뢰 |
| 저장소 계층 | SQL/영속성, 동시성 제어 | Controller에서 직접 SQL 조립 |
| AI 연계 | 근거 있는 제안·요약, 처리 상태 | 검증 없는 AI 출력으로 승인·제출 |

초기 운영 개발은 업무 기능별 모듈을 가진 하나의 Spring Boot 애플리케이션으로 시작하는 것을 권장한다. 서비스 분리는 배포·운영·조직상 독립성이 필요한 시점에 ADR로 결정한다. 현재 저장소 전체를 이동하는 작업은 이 규칙 채택과 별개다.

프런트 신규 기능은 `features/<업무>/` 단위로 확장하고 공통 UI는 `components/ui/`로 모은다. 백엔드는 업무 패키지 안에 API·서비스·저장소를 둔다. 기존 경로의 일괄 이동은 전용 리팩터링 PR에서 한다.

## 6. API와 데이터 계약

- API 연동 전 경로·HTTP 메서드·입출력 DTO·오류·권한·상태 전이·revision 조건을 함께 정한다. OpenAPI 등 기계 검증 가능한 계약으로 발전시키되 현재 설치됐다고 가정하지 않는다.
- JSON 필드는 lowerCamelCase, 오류는 제안된 `{code, message, fieldErrors, requestId}` 구조를 출발점으로 합의한다. 내부 스택·비밀값은 응답에 담지 않는다.
- 성공처럼 보이는 HTTP 200에 업무 실패를 숨기지 않는다. 인증·권한·검증·동시성 오류를 구분하고 정확한 상태 코드는 계약에서 확정한다.
- 목록의 page/size·정렬·필터 의미를 정한다. 제안 기본값은 0부터 시작하는 page, size 20, 최대 100이며 이는 Google 규칙이 아니다.
- 날짜만 나타내는 값과 시각을 구분한다. 시각은 시간대가 포함된 형식으로 교환하고 한국 사용자 화면의 표시는 Asia/Seoul 기준으로 처리한다.
- JavaScript 안전 정수 범위를 넘을 수 있는 DB 식별자는 문자열 계약을 검토한다. Java Long을 무조건 JSON 숫자로 노출하지 않는다.
- 변경 요청의 optimistic locking과 제출·게시 같은 명령의 멱등성을 설계한다. JSON revision 충돌과 HTTP If-Match 실패의 응답을 혼동하지 않는다.
- Oracle DB 도입 시 기관 키·유일성·외래키·이력·낙관적 잠금·조회 인덱스를 함께 검토한다. SQL은 바인드 변수를 사용한다.
- DB 변경 스크립트에는 순서·기존 데이터 영향·복구 계획을 적는다. 운영 데이터 삭제·스키마 초기화를 개발 편의 명령에 넣지 않는다.
- JPA/MyBatis, 마이그레이션 도구, ID 체계는 채택 ADR을 남긴다. 선택 전 두 방식을 혼용하지 않는다.

## 7. 보안길잡이 업무 수용 기준

| 상황 | 반드시 확인할 결과 |
|---|---|
| AI 후보 추출 | 근거·미확정 상태 표시, 확인 주체와 확인값 분리 |
| 파일 선택 | 명시적 전송·분석 행동 전 서버 전송을 시작하지 않음 |
| 담당자 검토 | 정보보안·ICT인프라 역할 및 순차/병렬 정책 반영 |
| 보완 답변 | 필요한 담당자 재검토 상태로 전환 |
| 중요 정보 변경 | 완료 검토의 유효성 재판정 |
| 최종 제출 | 필수값·미확정값·미해결 보완·검토 완료 검사, 제출본 보존 |
| 기관 설정 게시 | 초안과 게시본 구분, 기존 신청의 설정 버전 보존 |
| 오래된 화면에서 수정 | 충돌을 알리고 미저장 값 보존 |
| 다른 기관/사용자 접근 | 서버에서 조회·다운로드·변경 권한 거부 |
| 저장·AI·전송 실패 | 실패 상태와 재시도 수단, 성공으로 오표시하지 않음 |

이 표는 통합 개발의 수용 기준이다. 현재 시연 코드의 검사가 서버에서 보장되는 것으로 해석하지 않는다. UI 수치·토큰·접근성 상세는 design.md 한 곳에서 유지한다.

## 8. 테스트와 완료 조건

현재 실행 가능한 검사는 루트의 `npm run typecheck`, `npm test`, `npm run build`와 Java 21 환경의 `mvn -f backend/pom.xml verify`다. Docker 변경은 `docker compose config`와 기동·smoke 검사도 수행한다.

| 변경 종류 | 추가 확인 |
|---|---|
| 문서만 수정 | 링크·명령·현행 코드와의 일치 |
| UI·상호작용 | 역할별 흐름, 키보드, 오류·빈 상태, 좁은 화면 |
| 업무 상태·권한 | 정상 경로와 거부 경로, 중복·오래된 revision |
| API·DB | 계약 호환, 기관 범위, 트랜잭션·동시성, 실제 대상 DB 차이 |
| Docker·런타임 | 빌드, 서비스 준비 상태, 프록시, 종료·재시작 |
| AI 처리 | 합성 평가셋, 누락·근거 오류·악성 지시문·실패 처리 |

커버리지 숫자만으로 완료를 판정하지 않는다. 중요한 업무 규칙의 실패를 잡는 검사를 우선한다. 문서·단순 스타일 변경에 불필요한 테스트 코드를 추가하지 않는다.

PR 완료 조건: 수용 기준 충족, 필요한 문서·계약 갱신, 해당 검사 결과 기록, 시연/실제 구현 범위 표시, 미검증·후속 이슈 공개, 리뷰 완료. 테스트를 실행할 수 없으면 이유를 적고 통과라고 표시하지 않는다.

## 9. 포맷·CI 도입 순서

1. 이 규칙 초안을 리뷰하고 언어별 예외를 확정한다.
2. formatter/linter 버전을 고정한 설정 PR을 만든다. `CODING_STYLE.md`의 도입안을 따른다.
3. 기존 코드를 한 번 정리하는 포맷 전용 PR을 병합한다. 공개 계약과 업무 동작은 바꾸지 않는다.
4. 그 기준에서 format/lint/typecheck/test/build를 CI 필수 검사로 연결한다.
5. PR 템플릿·CODEOWNERS·branch protection을 실제 계정·저장소 환경에 맞춰 활성화한다.

설정 파일만 작성했다고 CI와 보호 규칙이 적용되는 것은 아니다. 현재 저장소에는 lint/format 스크립트, Spotless, Maven Wrapper가 없다.

## 10. 규칙 변경과 예외

규칙은 이유·적용 범위·검증 방법이 설명될 때 추가한다. “깔끔하게”, “모범적으로”처럼 판정할 수 없는 문장을 피한다. 예외에는 이유·영향·만료 조건 또는 재검토 이슈를 남긴다. 팀원은 규칙 변경을 PR로 제안하고, AI는 확정되지 않은 제안을 기존 결정처럼 취급하지 않는다.
