# 개발 아키텍처

React는 Next.js 안에서 화면 컴포넌트를 구성합니다. Next.js가 Spring Boot를 대체하지 않으며, 실제 서비스의 업무 규칙·인증·데이터 저장은 Spring Boot가 담당하도록 분리합니다.

| 계층 | 이번 코드 | 실제 서비스로 확장할 위치 |
| --- | --- | --- |
| React + Next.js | App Router, Client Component, 폼·표·모달 | URL별 화면 분할, 세션 기반 UI, 필요시 서버 렌더링 |
| 데이터 접근 | `gateway.ts`의 브라우저/API 어댑터 | 인증 쿠키 또는 BFF, 타임아웃·취소·오류 규격 |
| Spring Boot Controller | workspace 조회, command 실행 | 업무별 REST 명령, 서버에서 인증 주체·기관 확인 |
| Service | 데모 상태 전이·수정 버전 검사 | 트랜잭션, 검토 배정·완료 집계, 제출본 생성 |
| 저장소 | 메모리 합성 데이터 | Oracle 21c XE, JPA 또는 MyBatis Repository |
| AI | 미리 작성한 합성 요약 | 비동기 작업, 입력 버전 고정, 근거 검증, 제안/확정 분리 |

## 현재 실행 구조

- 웹 시연: Next.js 정적 출력 → React → 브라우저 저장 어댑터.
- 로컬 API 연결: 동일한 React UI → HTTP 어댑터 → Spring Boot → 메모리 저장소.
- UI가 데이터 저장 방식을 직접 결정하지 않도록 `loadWorkspace`, `executeCommand`에 접근을 모았습니다.
- 공개 웹 서버에 Spring Boot가 함께 배포되어 있지 않습니다. 별도의 JVM 런타임에서 실행해야 합니다.

## 유지해야 할 의미

1. AI 출력은 미확정 후보입니다. 원문이 있다는 이유로 확정하지 않습니다.
2. 사전 협의 완료, 최종 검토 완료, 실제 처리 완료는 다른 상태입니다.
3. 게시한 기관 설정은 새 신청에만 적용합니다.
4. UI 탭 이동은 업무 상태 변경이 아닙니다.
5. 완료 명령은 체크리스트·의견을 검증하고, 이력과 상태를 함께 변경합니다.
6. 실제 서버에서는 인증 사용자·기관·배정 역할을 검증해야 합니다. 이번 데모의 역할 선택값을 신뢰하면 안 됩니다.

## 다음 구현 순서

1. 화면을 목록·상세·기관 설정 라우트로 분할하고 `workspace.tsx`를 도메인별 컴포넌트로 분리.
2. 기관·사용자·소속·역할, 사업·신청·신청 개정, 배정 검토 작업을 DB에 연결.
3. `GET /security-requests`, `GET /security-requests/{id}`, `POST /review-tasks/{id}/decisions` 등 업무별 API로 어댑터 교체.
4. 질문·양식·검토 절차를 설정 게시 버전으로 묶어 신청에 연결.
5. 문서 업로드와 AI 추출 작업, 원문 근거와 담당자 확인 기능 연결.
6. 보완 답변·제출본 보존·재검토·처리 기록 추가.

## 제한 사항

프런트엔드의 localStorage 버전 검사는 편집 충돌을 보여 주는 데모입니다. 여러 탭의 동시 쓰기를 원자적으로 보장하지 않습니다. Spring Boot 샘플은 단일 JVM의 synchronized 명령 처리만 사용합니다. 실제 다중 서버에서는 DB 낙관적 잠금과 멱등성 키를 적용해야 합니다.

프로토타입 API의 단일 `/commands`와 전체 snapshot 응답은 빠른 UI 통합 목적입니다. 실제 서비스의 확정 API 명세로 간주하지 마세요.
