# 유비쿼터스 언어 — 업무 용어와 코드

작성일: 2026-11-07. FUNCTIONAL_SPEC v1.7의 업무 의미를 기준으로 신규 서버 API와 화면에서 사용한다. 아래 식별자는 이번 시작점의 구현 계약이며 향후 변경은 API 소비자와 함께 검토한다. 기존 `procedure` 호환 모델의 다른 이름을 새 업무 용어와 혼용하지 않는다.

## 객체와 경계

| 업무 용어 | 코드·API 식별자 | 의미·소유 경계 |
|---|---|---|
| 사업 건 | `BusinessCase`, `/api/business-cases` | 신청자가 설명한 사업. 공통 정보·답변을 한 번 수집하며 신청 1개 이상을 가짐 |
| 서류별 신청 | `SecurityRequest`, `/api/security-requests` | 서류 유형별 독립 업무 단위. 단계·상태·협의·반환·제출을 소유 |
| 서류 유형 | `DocType`, `docType` | `FIREWALL` 또는 `SECURITY_REVIEW`. 한 사업 건에 같은 유형은 한 건 |
| 공통 답변 | `AnswerValue`, `scope=CASE` | 사업 건 소유. 공통 정보 변경의 영향과 제출 스냅샷을 구별 |
| 서류별 답변 | `AnswerValue`, `scope=REQUEST` | 한 신청 소유. 다른 신청을 함께 전이시키지 않음 |
| 담당자 배정 | `Assignment` | 신청·분야별 활성 담당자. 검토 역할만으로 행위 권한이 생기지 않음 |
| 담당자 후보군 | `ReviewerPool` | 기관·분야별 담당자와 기본 배정자. 구체 구현·운영 범위는 API 계약 참조 |
| 분야별 협의 | `Review` | INFRA/SECURITY 각각의 검토. 할당 완료와 검토 완료를 분리 |
| 보완 요청 | `Supplement` | 대상 필드·사유·신청자 답변·요청 분야의 해결 확인을 보존 |
| 차수 반환 | `StageReturn` | 2→1, 3→2, 3→1, 4→3. 사유와 영향 필드를 남기고 기존 값 보존 |
| 처리 기한 | `Deadline` | 서버가 발생 시 영업일로 계산해 저장. 재산정은 이전 종료 + 새 기한 |
| 제출본 | `SecuritySubmission`, `SubmissionSnapshot` | 제출 시점의 공통·개별 답변과 설정 버전을 보존하는 불변 스냅샷. API 요약은 `SubmissionResponse` |
| 최종 확인 | `FinalConfirmation` | 4단계에서 특정 제출본을 INFRA→SECURITY 순으로 확인한 기록 |
| 감사 이력 | `AuditEvent` | 업무 변경과 같은 트랜잭션의 추가 전용 기록. 민감 원문은 포함하지 않음 |
| 설정 게시본 | `Publication`, `publicationVersion` | 새 신청에 적용할 설정 버전. 진행 중인 신청의 고정 버전과 구별 |
| 낙관적 잠금 버전 | `revision`, `expectedRevision` | 조회 당시 버전을 쓰기 요청에 실어 경쟁 변경을 409로 거부 |
| 현재 공통 정보 버전 | `caseRevision` | 신청 화면에서 공통 답변을 저장할 때 사용하는 사업 건 버전 |
| 업무 행동 힌트 | `allowedActions` | 화면 표시용 서버 계산값. 서버는 명령 실행 때 권한·조건을 다시 검사 |
| 불가 사유 | `blockers` | 현재 상태에서 진행할 수 없는 이유. UI 버튼 비활성화와 별도로 설명 |

## 사람·출처·확인

| 업무 용어 | 식별자 | 의미 |
|---|---|---|
| 신청자 | `APPLICANT` | 본인 사업·신청의 작성과 제출. 회원가입 기본 역할 |
| ICT인프라 담당자 | `INFRA` | 배정된 신청의 서버·통신 정보 할당·검토·최종 확인 |
| 정보보안 담당자 | `SECURITY` | 배정된 신청의 보안 검토·최종 확인·서류 확정 |
| 기관 관리자 | `ADMIN` | 기관 운영과 배정·역할 관리. 자동으로 검토자가 되지는 않음 |
| 사용자 답변 | `USER_ANSWER` | 사용자가 입력한 내용. 입력만으로 사실 확인이 끝나는 것은 아님 |
| AI 추론 | `AI_INFERRED` | 근거가 연결된 미확정 제안. AI가 기관 내부 사실을 만들어 내지 않음 |
| 담당자 입력 | `STAFF_INPUT` | 해당 책임을 가진 담당자의 입력 |
| 담당자 확인 | `STAFF_CONFIRMED` | 확인 행위와 확인 주체가 있는 값. 원출처와 확인 기록을 혼동하지 않음 |
| 사람의 확인 | `confirmation`, `confirmed` | 확인자·역할·시각. 출처와 별개로 표시·보존 |
| 미해당 | `notApplicable` | 질문이 적용되지 않는다는 명시적 답변. 미입력·잘 모름과 구분 |
| 확인 필요 | `source=null` 또는 미확정 답변 | 값이 없거나 출처·확인이 부족함. 이를 다섯 번째 출처로 저장하지 않음 |

## 신청 단계와 상태

| 단계 | 상태 식별자 | 사용자 문구 |
|---|---|---|
| 1 | `DRAFT` | 작성 중 |
| 2 | `CONSULTING` | 협의 중 |
| 2 또는 3 | `SUPPLEMENT_REQUESTED` | 보완 요청 |
| 3 | `FINAL_REVIEW` | 최종 검토 중 |
| 4 | `SUBMITTED` | 제출됨 |
| 4 | `FINALIZED` | 확정 |
| 종료 당시 단계 유지 | `CLOSED` | 종결(반려) |
| 종료 당시 단계 유지 | `WITHDRAWN` | 철회 |

사업 건의 상태는 저장하지 않고 하위 신청 상태를 요약한다. 신청의 “처리 완료/처리 불가”는 사용하지 않는다. `FINALIZED`·`CLOSED`·`WITHDRAWN`은 종료 상태이며 조회·다운로드만 허용한다. `SUBMITTED`는 아직 확정이 아니다.

## 완료라는 말의 대상

| 표현 | 의미 | 다음에 남는 일 |
|---|---|---|
| INFRA 할당 완료 | 필요한 서버·IP·포트 등의 담당자 정보가 준비됨 | INFRA 자체 검토, SECURITY 검토 |
| 협의 완료 | 필요한 두 분야의 검토가 완료됨 | 사용자 최종 검토·미확정값 확인·제출 |
| 제출 완료 | 사용자가 불변 제출본을 생성함 | 두 분야 최종 확인·SECURITY 확정 |
| 서류 확정 | 해당 제출본을 담당자가 최종 확정함 | 방화벽 실제 적용은 별도 업무 |
| 방화벽 적용 기록 | 실제 처리 결과를 INFRA가 기록함 | F-15 P2 후속 범위; 현재 시작점에서 미구현 |

P2의 `FirewallRule`, 지표(`insight`), 알림(`Notification`)은 명세상 설계 용어다. 해당 테이블·화면 설명이 있더라도 실행 API와 검증이 없으면 구현 완료로 표시하지 않는다.
